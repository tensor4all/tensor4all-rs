# Issue #792: cached global pivot readout

## Decisions

- Keep one `TreeTNCachedEvaluator` per global pivot search and evaluate the full candidate batch together. This shares subtree environments across candidate points; splitting by varied site was slower on the recorded workloads.
- Keep `TreeTN::evaluate` as the pointwise reference path in tests so fixed-seed searches can compare the chosen pivots against the cached readout, for f64 and for f32/Complex32 on a swept branched (degree-3) state.
- Switch the search's seed RNG from `StdRng` to the named `ChaCha8Rng` in this change, as REPOSITORY_RULES requires for seed-based production entry points. This changes fixed-seed trajectories, so the recorded pivots and error histories in the unit tests were re-recorded. Keeping the switch was decided by a 200-seed comparison with a criterion fixed beforehand (below). Splitting it into a separate PR was the rejected alternative; it would only move the same trajectory change.

## Verification conclusions and constraints

- On current HEAD `d93b3e5e`, a paired release rerun with the same `ChaCha8Rng` and benchmark source produced identical evaluation counts, rank and error histories, pivot fingerprints, sampled-result fingerprints, and sampled relative errors between pointwise and cached readouts. The three cases measured median paired speedups of 47.00x, 25.10x, and 28.29x. Full measurements, binary hashes, and host conditions are in the [benchmark report](../../benchmarks/results/2026-09-30-treetci-global-search.md#rerun-on-current-head-with-chacha8rng).
- An earlier rerun on the #793 base is excluded as a validity failure: its pointwise baseline ran at cached-readout speed. Both of its binaries had been built into one shared target directory. A clean rebuild with separate targets and distinct hashes gave 16-17 s for the pointwise baseline. Hashes and times are in the [benchmark report](../../benchmarks/results/2026-09-30-treetci-global-search.md#excluded-run-validity-failure).
- The RNG switch is quality-neutral on the three benchmark cases over 200 seeds each. Every run of both RNGs stopped after 4 iterations at the same final rank, and neither had a false convergence. `ChaCha8Rng` medians of evaluations and sampled error lie inside the `StdRng` interquartile ranges, and worst errors are of the same order. The seeds overlap (a run uses four consecutive search seeds); the independent-seed subset agrees. In `rand` 0.9, `StdRng` is ChaCha12. Details are in the [RNG section](../../benchmarks/results/2026-09-30-treetci-global-search.md#rng-switch-stdrng-versus-chacha8rng-200-seeds). The result covers three workloads at one tolerance, not every target function.
- A current-HEAD diagnostic compared both readouts on every candidate batch in 36 global searches across the three fixtures. Readout differences reached `1.45e-15` relative to the largest `|tt|`; the nearest best-error threshold was `9.11e-8` away. No per-start winner, threshold acceptance, or final pivot order changed. Detailed margins are in the [benchmark report](../../benchmarks/results/2026-09-30-treetci-global-search.md#current-head-readout-rounding-diagnostic).
- The benchmark covers three deterministic fixtures with three paired process runs. It is a post-implementation exploratory rerun, not a predeclared promotion gate or a confidence-interval study. The margin diagnostic supports these workloads but does not establish stability for inputs deliberately constructed near the acceptance threshold.
- Remaining constraints: `SimpleProposer` and `TruncatedDefaultProposer` still seed a `SmallRng` through `DefaultHasher`, which is neither a named RNG nor portable. The search also lacks the caller-owned `&mut R` API that REPOSITORY_RULES asks for. Both are left as follow-ups.
