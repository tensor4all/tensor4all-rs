# tenferro v0.7.0 dependency bump: paired 1T benchmarks

Date: 2026-09-23.

- Baseline: tensor4all-rs `4fee1a327ed6b1861fa1d0ea36a00559d0fe078f` (origin/main,
  tenferro pin `0457a2ed0aeea21b14f4297f7f4731e09b3a0507`), built in a throwaway
  worktree so each revision kept its own `target/`.
- Candidate: tensor4all-rs `1e5253e77e69cd7f42f0c8e4668adc889364ac27` (tenferro pin
  `412852a8cfb13b14246443fc09b1c0c34f5ce1cd`, the v0.7.0 release commit).

Machine: one workstation (64 logical CPUs), CPU affinity pinned to core 2,
Rayon/BLAS/OMP/MKL/OpenBLAS thread counts forced to one. `taskset` sets the mask
for every thread of a process, so the effective parallelism is one CPU even
though the `benchmark_tt_ops` process peaked at three threads (`/proc/<pid>/status`
maximum: tensor_ops candidate 1, baseline 2; tt_ops 3 on both sides). Cargo
`-j 16` applies to builds only.

The `benchmark_tt_ops` and `benchmark_tensor_ops` runs are paired: each pair runs
candidate then baseline, and the next pair reverses the order, so drift affects
both sides. SRC gate pairs alternate direction inside the runner.

## Commands

```bash
# 1T paired runs, 3 pairs for tt_ops and 6 for tensor_ops
RAYON_NUM_THREADS=1 BLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 \
  taskset -c 2 <example binary> [args]

# SRC gate (both binaries built with T4A_BENCH_GIT_COMMIT=<revision>)
python3 scripts/run-src-benchmark-gates.py \
  --baseline <baseline worktree>/target/release/examples/benchmark_src \
  --baseline-commit 4fee1a327ed6b1861fa1d0ea36a00559d0fe078f \
  --candidate target/release/examples/benchmark_src \
  --candidate-commit 1e5253e77e69cd7f42f0c8e4668adc889364ac27 \
  --suite quick --pairs 20 --reps 3 --allowed-regression-percent 5 \
  --expected-backend tenferro --expected-features tenferro-cpu-faer \
  --output benchmarks/results/2026-09-23-tenferro-v0.7.0-src-quick.json
```

## Findings

- **No metric regressed.** The worst candidate/baseline ratio in any of the three
  suites is `0.977` (`tensor4all_directsum_mps`, L=32 chi=8), i.e. 2.3 % faster;
  every other metric is between `0.60` and `0.96`.
- **Numerics are unchanged.** Every exact checksum in `benchmark_tt_ops` and
  `benchmark_tensor_ops` is bit-identical between the two sides. The SRC gate
  relative errors stay at `1e-18`–`1e-26` against a `1e-8` tolerance.
- **The only moving value is approximate zip-up.** `tensor4all_zipup_mpo_prepared`
  shows 3 (chi=4) and 2 (chi=8) distinct values across the six runs, including
  within one side. The real parts are identical; only the `1e-11`-relative
  imaginary residue varies. v0.7.0 states that float `sum`/`max`/`min` reductions
  no longer promise a fixed accumulation order, which explains the residue.
- **The `conj` cases moved the most** (`ratio 0.60`–`0.64`) and `benchmark_tensor_ops`
  as a whole moved by `0.70`–`0.92`; the eager/leaf and strided-kernel changes in
  v0.6/v0.7 are the plausible cause, though this suite does not attribute it.

## Limits of this evidence

- One machine, one thread, one session. The repeating `/proc` thread-count sample
  bounds the observed thread count but does not prove that no transient worker ran
  outside the pinned CPU set; affinity pinning is the actual guarantee.
- The quick SRC suite is four small cases (4.8–25.3 ms baseline). A first run with
  `--pairs 5` was `FAIL`: `tree-n7-b4-adaptive` (5–15 ms) had a CI95 upper bound of
  `1.0544` against the declared `1.050` while its paired median was `0.980`. The
  20-pair/3-rep run above is the recorded result; the 5-pair failure is kept here
  so the reader can weigh the sample size rather than only the verdict.
- `benchmark_tensor_ops` reports `per_call_us` from an in-process repeat count, not
  the paired bootstrap the SRC runner uses, so its `0.70`–`0.92` band carries the
  5–10 % run-to-run spread shown in the raw records.
- CUDA, `ci`-profile and hosted-CI lanes were not exercised here.
